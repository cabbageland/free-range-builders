## Executive summary
[`ponytail`](https://github.com/DietrichGebert/ponytail/tree/2ed6c52c9d7e5e56942508591085fd45dea277d3) is best understood as behavioral middleware for coding agents, not as a single prompt. The public pitch in [`README.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/README.md) sells the "lazy senior dev" persona, but the real product lives in [`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md), [`hooks/ponytail-instructions.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-instructions.js), and [`hooks/ponytail-runtime.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-runtime.js). Those files define the canonical ladder, filter it by intensity, and persist the active mode via a tiny state-file contract.

The second important fact is that the repo is shipping the same behavior through several delivery paths. [`.codex-plugin/plugin.json`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/.codex-plugin/plugin.json) wires the rules into Codex-style plugin hooks. [`pi-extension/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/pi-extension/index.js) adapts the same mode model to Pi's session, UI status, and pre-agent events. [`ponytail-mcp/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/ponytail-mcp/index.js) exposes the ruleset as both an MCP prompt and a read-only tool for hosts that cannot do always-on injection.

The strongest builder move is that the repo does not stop at rhetoric. [`benchmarks/results/2026-06-18-agentic.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/benchmarks/results/2026-06-18-agentic.md) documents a real A/B harness against Claude Code on a public repo and even admits an earlier contamination bug where the baseline had secretly loaded Ponytail. The weak side is obvious from the tree: a lot of adapter code now exists to preserve one behavior across many fast-moving agent products.

## What they built
They built a cross-agent plugin-and-skill package that tries to force a consistent implementation bias: ask whether the thing should exist at all, then prefer reuse, then stdlib, then native platform features, then already-installed dependencies, then the smallest custom code that survives.

That high-level rule is packaged in several concrete surfaces:

- a canonical instruction source in [`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md)
- lifecycle-hook adapters in [`hooks`](https://github.com/DietrichGebert/ponytail/tree/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks)
- per-host plugin metadata such as [`.codex-plugin/plugin.json`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/.codex-plugin/plugin.json) and [`.qoder-plugin/plugin.json`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/.qoder-plugin/plugin.json)
- slash-command style aliases in [`commands`](https://github.com/DietrichGebert/ponytail/tree/2ed6c52c9d7e5e56942508591085fd45dea277d3/commands)
- a standalone MCP server in [`ponytail-mcp`](https://github.com/DietrichGebert/ponytail/tree/2ed6c52c9d7e5e56942508591085fd45dea277d3/ponytail-mcp)
- an evaluation harness in [`benchmarks`](https://github.com/DietrichGebert/ponytail/tree/2ed6c52c9d7e5e56942508591085fd45dea277d3/benchmarks)

## Why it matters
Most agent "skills" are brittle because they are one-shot prompt text. They do not survive restarts, they do not show a durable current mode, and they do not attach themselves to subagents consistently.

Ponytail matters because the source shows a different bet:

1. Keep one canonical instruction body.
2. Turn mode selection into persisted state.
3. Inject that state at the host's lifecycle boundary instead of hoping the user remembers to paste the same prompt every time.
4. Benchmark the result on real code diffs, not just "the answer felt shorter."

That is a reusable pattern even if you do not like this repo's exact philosophy.

## Layered architecture dissection
### High-level system shape
The high-level flow is: define the full ruleset once, resolve the current mode from environment or config, persist that mode to a shared state file, inject the filtered rules at host lifecycle events, expose user-facing command aliases to switch modes, and validate the behavior with a benchmark harness plus regression tests.

### Main layers
**1. Canonical behavior layer**  
[`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md) is the actual product contract. It defines the ladder, the mode table, the deactivation phrases, and the boundary conditions for when "lazy" must stop and correctness or safety must win.

**2. Config and state layer**  
[`hooks/ponytail-config.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-config.js) resolves default mode from `PONYTAIL_DEFAULT_MODE`, per-user config, and fallback defaults. [`hooks/ponytail-runtime.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-runtime.js) turns that into a shared `.ponytail-active` state file plus host-specific hook output shapes.

**3. Instruction synthesis layer**  
[`hooks/ponytail-instructions.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-instructions.js) is more important than it first looks. It does not duplicate rules by hand. It reads [`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md), strips frontmatter, and filters only the mode-specific intensity rows and worked examples. That keeps one canonical instruction body while still supporting `lite`, `full`, `ultra`, and the independent `review` mode.

**4. Lifecycle injection layer**  
[`hooks/ponytail-activate.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-activate.js) activates the default mode on session start, emits hidden context, and even nudges statusline setup. [`hooks/ponytail-mode-tracker.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-mode-tracker.js) watches user prompts for `/ponytail` switches, persists default-vs-session mode correctly, and includes timeout logic so a swallowed stdin EOF does not freeze the session.

**5. Host adapter layer**  
[`.codex-plugin/plugin.json`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/.codex-plugin/plugin.json) defines a Codex-facing package with hooks and skills. [`pi-extension/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/pi-extension/index.js) adds status UI, command parsing, session entry inspection, and pre-agent system prompt injection. [`ponytail-mcp/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/ponytail-mcp/index.js) offers a fallback delivery mode for hosts that can consume MCP prompts or tools but not lifecycle hooks.

**6. Evidence layer**  
[`benchmarks/README.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/benchmarks/README.md) documents the older single-shot benchmark, while [`benchmarks/results/2026-06-18-agentic.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/benchmarks/results/2026-06-18-agentic.md) explains the more serious agentic harness. [`tests/behavior.test.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/tests/behavior.test.js) is small but telling: the repo tests the benchmark grader itself, not just the plugin code.

### Request / data / control flow
1. The source rules begin in [`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md).
2. [`hooks/ponytail-config.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-config.js) resolves the default mode and relevant env overrides.
3. [`hooks/ponytail-instructions.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-instructions.js) filters the instruction body to the effective mode.
4. [`hooks/ponytail-activate.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-activate.js) writes the mode flag and injects the hidden context at session start.
5. [`hooks/ponytail-mode-tracker.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-mode-tracker.js) updates or clears mode based on user commands, then re-injects rules where the host needs it.
6. Host adapters like [`pi-extension/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/pi-extension/index.js) or [`ponytail-mcp/index.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/ponytail-mcp/index.js) translate that shared mode model into UI status, slash commands, or MCP prompt/tool calls.

## Practical questions and answers
**Is this just a single prompt with a good README?**  
No. The core rules are prompt text, but the repo wraps them in state management, lifecycle hooks, per-host manifests, commands, and tests. That is a different product shape from a normal "copy this system prompt" repo.

**Where does persistence actually come from?**  
From [`hooks/ponytail-runtime.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-runtime.js), which writes the active mode to `.ponytail-active`, and [`hooks/ponytail-config.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-config.js), which resolves the default mode from env or config.

**What is the sharpest implementation idea here?**  
Keeping one canonical ruleset and adapting it through thin host layers. [`hooks/ponytail-instructions.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/hooks/ponytail-instructions.js) is the key file because it avoids a drift-prone copy of the instructions per adapter.

**Where is it most likely to break?**  
At host boundaries. This repo depends on lifecycle event names, hidden-context injection behavior, plugin manifest semantics, and stdin/stdout hook contracts that can change under it.

**How much should we trust the benchmark claims?**  
Trust them more than the typical plugin repo, but still read them skeptically. The good sign is that [`benchmarks/results/2026-06-18-agentic.md`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/benchmarks/results/2026-06-18-agentic.md) explicitly admits where earlier numbers were flattering for the wrong reason.

## What is smart
- One canonical ruleset with filtered mode variants instead of one prompt file per platform
- Turning behavior into persisted mode plus lifecycle injection, not just a paste-once instruction
- Shipping multiple delivery paths, including a standalone MCP fallback, without changing the core philosophy
- Testing the benchmark grader in [`tests/behavior.test.js`](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/tests/behavior.test.js) so the evaluation harness is not pure theater
- Documenting the contamination bug in the benchmark writeup instead of burying it

## What is flawed or weak
- The repo now carries a lot of platform-specific packaging and hook logic, which is expensive to keep correct
- The README voice is intentionally theatrical, so you have to read past the brand to reach the engineering substance
- The behavior is still instruction-following, not a hard semantic guarantee; a model can always ignore the ladder
- Some benchmark claims are easy to oversimplify unless you read the "honest measurement" caveats closely

## What we can learn / steal
- Keep one canonical behavior spec and compile it into host-specific adapters
- Use lifecycle hooks to make agent preferences durable across sessions and subagents
- Treat benchmark harnesses as first-class product assets, not marketing afterthoughts
- Persist mode in the simplest possible form first, then add richer UI or command affordances later

## How we could apply it
If we wanted an internal "coding style governor" for our own agents, I would copy Ponytail's architecture more than its persona: one authoritative ruleset, one shared mode/state layer, thin adapters per host, and a benchmark suite that measures actual repository diffs. I would keep the branding quieter and the supported host list smaller, because cross-ecosystem drift is the main maintenance tax this repo is taking on.

## Bottom line
`ponytail` is worth studying because it answers a real operational question: how do you make an agent preference stick across sessions, hosts, and subagents without copying prompt text everywhere?

The reusable builder lesson is that prompt engineering gets more durable when you treat it like software packaging: one source of truth, thin adapters, persistent state, and tests around the claims.
