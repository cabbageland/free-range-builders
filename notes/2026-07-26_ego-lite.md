## Executive summary
`ego-lite` is not mainly an open-source browser engine. The real open-source center of gravity is the helper/runtime layer in [`package/ego-browser`](https://github.com/citrolabs/ego-lite/tree/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser), plus the skill package in [`skills/ego-browser`](https://github.com/citrolabs/ego-lite/tree/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser). The browser ships a native `globalThis.ego` runtime, and this repo wraps that runtime in a Playwright-shaped JavaScript surface that agents can call in one heredoc instead of one tool call at a time.

The strongest design move is visible in [`package/ego-browser/src/helpers.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/helpers.ts) and [`package/ego-browser/src/run.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/run.ts): the agent gets a small set of typed facades like `page`, `browser`, `taskSpaces`, `site`, `fetch`, and `cdp`, then writes one coherent script that executes against the live browser. That is a different control model from "call click, then inspect output, then call fill, then inspect output."

The second strong move is that reusable experience is treated as code and manifests, not just prompt lore. [`skills/ego-browser/learnings/google/manifest.json`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser/learnings/google/manifest.json), [`skills/ego-browser/learnings/google/tools/search-extract.js`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser/learnings/google/tools/search-extract.js), and [`skills/ego-browser/learnings/google/browser-tools/autocomplete.js`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser/learnings/google/browser-tools/autocomplete.js) show a clean pattern for site-specific notes plus node-side and browser-side tools.

## What they built

- [`package/ego-browser/src/index.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/index.ts) installs the SDK into a target runtime and exposes legacy helper names.

## Why it matters
This repo matters because it treats browser automation for agents as a runtime-design problem, not just a better-prompt problem.

1. It keeps the browser as the primary product and the agent surface as a typed embedded runtime, instead of forcing the agent to puppeteer a disposable side browser.
2. It makes isolation explicit with task spaces and handoff semantics, which is exactly where most "agent can use your browser" demos get mushy.
3. It starts building reusable site intelligence as manifests, notes, and code, instead of leaving everything as per-run rediscovery.

## Layered architecture dissection
### High-level system shape
The shape is: agent heredoc or SDK install -> helper facades -> browser runtime bridge -> CDP/session layer -> driver helpers -> optional site-specific learnings. The browser itself owns tabs, task spaces, snapshots, and CDP transport. The open-source TypeScript layer owns ergonomics, policy, and reuse.

### Main layers
**1. Packaging and entry layer**  
[`package/ego-browser/package.json`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/package.json) bundles the runtime into one ESM binary, exposes `ego-browser`, and wires `build`, `test`, `mutation-check`, and `validate:site-skills`.

**2. CLI and SDK layer**  
[`src/run.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/run.ts) reads stdin, builds the helper context, executes the heredoc, and routes `console.log` through a buffered sink. [`src/index.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/index.ts) installs the same helper surface into a live runtime and wraps browser/task-space mutators so they invalidate stale sessions when needed.

**3. Browser bridge layer**  
[`src/browser-runtime.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/browser-runtime.ts) is the boring but crucial machinery. It serializes CDP messages, attaches to the preferred or active target, enables page events, buffers browser events, and retries once when a session is lost.

**4. Helper facade layer**  
[`src/helpers.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/helpers.ts) defines the public shape agents actually see. `page`, `browser`, `taskSpaces`, `site`, `fetch`, and `cdp` are cleaner abstractions than dumping raw CDP or a general shell into the agent's lap.

**5. Observation and ref layer**  
[`src/driver/observe.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/driver/observe.ts), [`src/ref-state.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/ref-state.ts), and [`src/driver/element-ops.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/driver/element-ops.ts) show the snapshot/ref model. Snapshots produce references, refs lazily refresh themselves when needed, and element handles are resolved and released through one path.

**6. Learned site layer**  
[`src/learning/index.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/learning/index.ts) loads learned notes and tool signatures for a URL. [`skills/ego-browser/learnings/google/manifest.json`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser/learnings/google/manifest.json) shows the schema, while the `google` and `x-com` learning directories demonstrate the intended packaging pattern.

**7. Verification layer**  
[`package/ego-browser/scripts/real-browser-e2e/runner.mjs`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/scripts/real-browser-e2e/runner.mjs) runs real-browser smoke tests and case suites. That is a better signal than a repo that only unit-tests mock DOM helpers.

### Request / data / control flow
1. A user or agent invokes `ego-browser` with a heredoc, which lands in [`run.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/run.ts).
2. [`helperContext()` in `helpers.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/helpers.ts) builds the facades and help surface.
3. Helper calls like `page.snapshot()` or `browser.openOrReuseTab()` eventually pass through [`browser-runtime.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/browser-runtime.ts) and [`cdp-eval.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/cdp-eval.ts).
4. Observation helpers populate ref state through [`observe.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/driver/observe.ts) and [`ref-state.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/ref-state.ts).
5. If a site learning exists, the `site` facade can load notes and invoke node-side or browser-side tools declared in [`learning/index.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/learning/index.ts).

## Practical questions and answers
**Is this repo the browser itself?**  
Not really. The most inspectable part here is the agent runtime and skill packaging around the browser. The kernel-level snapshotting and native browser internals are product claims in [`README.md`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/README.md), not source you can fully audit here.

**Why is the heredoc model interesting?**  
Because [`run.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/run.ts) and [`helpers.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/helpers.ts) let the agent compose a multi-step browser script in one execution round. That reduces tool-chatter and keeps intermediate logic in code instead of in repeated conversational turns.

**Where should a builder start reading?**  
Start with [`package/ego-browser/README.md`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/README.md), then [`src/run.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/run.ts), [`src/helpers.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/helpers.ts), [`src/browser-runtime.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/browser-runtime.ts), and [`src/learning/index.ts`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/src/learning/index.ts).

## What is smart
- The agent-facing surface is deliberately narrow and code-like instead of raw-shell-like.
- Task-space ownership and handoff are explicit first-class concerns, not undocumented product magic.
- Site-specific experience is packaged as manifests, notes, node tools, and browser tools.
- The repo tests against the real browser bridge with [`runner.mjs`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/package/ego-browser/scripts/real-browser-e2e/runner.mjs), not only mocked unit tests.

## What is flawed or weak
- The most important proprietary claims, especially the browser internals and "kernel-level customization" language in [`README.md`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/README.md), are not inspectable here.
- The public repo is heavily weighted toward the helper package and skills, so you are auditing the control plane more than the browser substrate.
- The whole system is still macOS-first, as the install flow in [`skills/ego-browser/references/install.md`](https://github.com/citrolabs/ego-lite/blob/02ee972edf0685371c826c90421511f8a2940cd5/skills/ego-browser/references/install.md) makes plain.
- Hand-authored site learnings are powerful, but they create a maintenance burden and can quietly drift if not continuously validated.

## What we can learn / steal
- Give agents typed task objects and facades instead of a giant generic tool bag.
- Treat human-agent browser sharing as a control and ownership problem, not only a selector problem.
- Store reusable site knowledge as source-controlled manifests, notes, and executable tools.
- Run browser automation verification against the real browser surface early.

## How we could apply it
If we built our own browser automation stack, I would copy the runtime pattern, not the branding: one compact agent execution surface, explicit workspace ownership, a snapshot-plus-ref observation model, and a first-class path for domain-specific learnings.

## Bottom line
`citrolabs/ego-lite` is worth studying because it is one of the clearer attempts to turn "agent uses your browser" from a demo gimmick into a runtime architecture.

The builder lesson is that the valuable part is not another click helper. It is the control plane: isolated task spaces, typed browser facades, learned site tools, and an execution model that lets the agent do a whole browser maneuver in code instead of in tool-call stutter.
