# Macro

- Repo: `macro-inc/macro`
- URL: https://github.com/macro-inc/macro
- Date: 2026-08-12
- Repo snapshot studied: `main` @ `00ce2a40d00cde03a6dba26faf219905d5f5654f`
- Why picked today: GitHub daily trending showed `325 stars today` when checked, and the repo is a serious attempt to open-source a full work operating system instead of yet another narrow AI wrapper. The tree is also inspectable in the right places: a large Rust workspace, a SolidJS client, a Cloudflare sync worker, and a real MCP service wired into product objects.

## Executive summary
`macro` is not one clever frontend pretending to be a platform. The source tree shows a deliberately split system: a large Rust workspace in [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/Cargo.toml), a big client app in [`apps/web`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web), product-specific backend services in [`services`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/services), and dozens of domain crates in [`crates`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates). The repo is trying to make the "one workspace for email, chat, docs, tasks, CRM, and agents" claim true by pushing everything into one shared graph and one shared set of service boundaries rather than stitching together acquired products.

The strongest proof is the combination of three files. [`crates/complete_graph/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph/src/lib.rs) explicitly composes multiple GraphQL adapter crates into one shared schema. [`services/mcp_service/src/main.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/src/main.rs) exposes the DCS AI toolset over a Streamable HTTP MCP server instead of keeping the product's capabilities trapped inside the web app. [`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml) shows a separate Cloudflare-based document sync plane with Durable Objects, D1, R2, and KV bindings. That is real systems architecture, not just branding.

The weakness is scope. `macro` is trying to be email, chat, docs, CRM, calls, agents, and sync infrastructure at once. The engineering surface is impressive, but the blast radius is huge and the architecture inherits all the usual monorepo and multi-product complexity risks: permissions drift, schema sprawl, sync edge cases, and a lot of places where "unified" can quietly become "tightly coupled."

## What they built
They built an integrated work platform with a few distinct layers visible in the repo:

- A shared Rust workspace in [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/Cargo.toml) that declares dozens of domain crates and services.
- A large client application in [`apps/web`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web), whose [`package.json`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web/package.json) shows SolidJS, Lexical, Loro CRDT, Tauri, TanStack Query, and LiveKit in one interface layer.
- A graph-composition layer in [`crates/complete_graph`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph) that merges channel, email, notification, permission, property, and entity mutation adapters into one schema.
- A memory subsystem in [`crates/memory`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/memory), whose [`src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/memory/src/lib.rs) fans out into `config`, `domain`, `inbound`, and `outbound` modules instead of burying memory logic in a single prompt file.
- An MCP exposure layer in [`services/mcp_service`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service), with [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/Cargo.toml) wiring in chat, documents, email, CRM, reminders, notification, queues, auth, and `rmcp`.
- A dedicated collaboration/sync plane in [`services/sync-service`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service), configured in [`wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml).

## Why it matters
Many "AI workspaces" are really a prompt layer on top of Slack, Gmail, Notion, and Linear. `macro` matters because it is trying to remove the seams instead of decorating them.

That matters for builders for three reasons:

1. The shared graph idea is architectural, not cosmetic. If email threads, docs, CRM records, tasks, and messages all live in the same schema, cross-linking and AI tool access become product primitives instead of brittle integrations.
2. The MCP layer is product-native. [`services/mcp_service/src/main.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/src/main.rs) says the same toolset used in the product's chat/stream API is available over HTTP MCP, which is a much stronger story than "we added a chatbot tab."
3. The collaboration layer is separated into its own runtime. [`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml) suggests the team understands that document sync has different latency and state-management needs than a normal CRUD backend.

## Repo shape at a glance
The repo shape is monorepo-heavy but not chaotic:

- [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/Cargo.toml) is the top-level map. It enumerates a long list of domain crates and services, plus build tooling like [`tooling/xtask`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/tooling/xtask).
- [`apps`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps) contains user-facing applications, including [`apps/web`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web) and [`apps/docs`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/docs).
- [`crates`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates) is the domain and platform core: graph composition, email, CRM, chat, permissions, memory, search, auth, eventing, and shared models.
- [`services`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/services) is the runtime layer: MCP, sync, notification, email, search processing, upload extraction, websocket, and more.
- [`infra`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/infra), [`docker`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/docker), [`nix`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/nix), and [`static_assets`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/static_assets) round out deployment, developer environment, and shipped assets.

## Layered architecture dissection
### High-level system shape
The high-level shape is: a large SolidJS/Tauri client drives a shared graph-backed backend; domain logic is factored into many Rust crates; specialized services expose collaboration, ingestion, search, notification, and agent surfaces; and the AI-facing capabilities are exported through a first-class MCP service rather than bolted on as an afterthought.

### Main layers
**1. Client experience layer**  
[`apps/web/package.json`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web/package.json) tells you what kind of client this is. `solid-js` and `@solidjs/router` suggest a performance-first web app, `lexical` and `@macro-inc/lexical-core` back the editing surface, `loro-crdt` and `@macro-inc/collaboration` point to collaborative data structures, `@tauri-apps/api` implies a desktop path, and `livekit-client` shows calls are a real subsystem, not a placeholder page.

**2. Shared graph and schema layer**  
[`crates/complete_graph/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph/src/lib.rs) is one of the clearest architecture files in the repo. It literally describes itself as the composition of multiple domain GraphQL adapter crates into the complete schema. That is the technical version of Macro's "everything is @linked" promise.

**3. Product-domain crate layer**  
The workspace members in [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/Cargo.toml) show the domain decomposition: `crm`, `email`, `chat`, `memory`, `embedding`, `entity_mutation`, `macro_event_broker`, `macro_queues`, `search_service`, and many more. This is not a single service with giant folders; it is a product platform broken into many compile-time boundaries.

**4. Agent and tool exposure layer**  
[`services/mcp_service/Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/Cargo.toml) and [`services/mcp_service/src/main.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/src/main.rs) show a serious MCP surface. The service uses `rmcp`'s Streamable HTTP server, OAuth-backed auth via `mcp_auth_proxy`, and tool dependencies spanning chat, documents, email, CRM, notifications, reminders, and search. That means agent access is wired into real app surfaces, not just a thin wrapper over one assistant endpoint.

**5. Collaboration and sync layer**  
[`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml) is unusually revealing. It configures Durable Objects for `DocumentSyncSession`, D1 databases, R2 snapshot buckets, KV namespaces, and multiple environments. That strongly suggests the team treats collaborative document state as edge infrastructure with specialized persistence and replay requirements.

**6. Memory and synthesis layer**  
[`crates/memory/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/memory/src/lib.rs) is tiny but informative because it exposes separate `config`, `domain`, `inbound`, and `outbound` modules. That is a better sign than a single `memory_prompt.md` file. It suggests Macro's "nightly memory synthesis" story is backed by a real subsystem boundary.

### Request / data / control flow
1. A user operates through the client in [`apps/web`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web), whose dependencies show editing, collaboration, queries, and calls in one interface layer.
2. Domain requests fan into Rust crates in [`crates`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates), where entities like channels, email, CRM records, properties, and notifications are modeled separately.
3. Cross-domain queries are composed through [`crates/complete_graph/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph/src/lib.rs), which is the schema glue for the linked workspace story.
4. Collaborative document state is handled through the separate worker configured in [`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml), using edge-native persistence and session infrastructure.
5. AI and external-agent actions flow through [`services/mcp_service/src/main.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/src/main.rs), which exposes authenticated tools over HTTP rather than inventing a second-class automation path.
6. Long-lived context and synthesis appear to route through the separate memory subsystem in [`crates/memory`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/memory).

## Practical questions and answers
**Is this really one system, or many apps marketed as one?**  
More one system than most. [`crates/complete_graph/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph/src/lib.rs) is compelling evidence that multiple product domains are being intentionally composed into one schema rather than merely linked by URLs.

**Where does the collaborative-doc story actually live?**  
Partly in the client dependencies from [`apps/web/package.json`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web/package.json), which include `loro-crdt`, and partly in the dedicated worker configured by [`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml). That is a believable architecture for realtime documents.

**What makes the AI layer more real than usual?**  
[`services/mcp_service/src/main.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service/src/main.rs) serves the same DCS toolset over HTTP MCP with auth and session management. That is much stronger than a repo that only says "AI-native" in a README.

**What is most likely to fail first in production?**  
Coordination cost. This many domain crates and services increase the chance of permissions bugs, schema drift, synchronization anomalies, and high-cognitive-load releases. The architecture is coherent, but coherence at this scale is expensive to preserve.

## What is smart
- Using a graph-composition layer like [`crates/complete_graph/src/lib.rs`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/crates/complete_graph/src/lib.rs) to make cross-product linking a backend primitive.
- Shipping a real MCP service in [`services/mcp_service`](https://github.com/macro-inc/macro/tree/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/mcp_service) instead of trapping agent tooling inside proprietary UI endpoints.
- Separating collaboration sync into its own Cloudflare worker configured by [`services/sync-service/wrangler.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/services/sync-service/wrangler.toml).
- Building the client around strong primitives for editing, collaboration, and desktop packaging, visible in [`apps/web/package.json`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/apps/web/package.json).

## What is flawed or weak
- The product scope is massive, which means the repo has a correspondingly massive coordination burden.
- The workspace size in [`Cargo.toml`](https://github.com/macro-inc/macro/blob/00ce2a40d00cde03a6dba26faf219905d5f5654f/Cargo.toml) hints at a lot of compile-time and ownership complexity.
- The README sells a sweeping vision; the inspected files prove a lot, but not every bold product claim is equally auditable from the source slices.
- A unified system can become a tightly coupled system if schema and service boundaries are not defended aggressively over time.

## What we can learn / steal
- Use one shared graph or schema composition layer if the product promise depends on deep cross-linking.
- Expose internal product capabilities through a standard tool protocol like MCP instead of inventing a separate automation universe.
- Give collaborative state its own runtime and persistence model rather than hiding it inside the main API service.
- Keep memory as a distinct subsystem boundary, not as an unstructured prompt artifact.

## How we could apply it
If we ever build our own workspace or knowledge tool, I would copy Macro's structural instincts, not its entire scope. The most reusable pattern is: shared domain graph, real external tool surface, collaboration-specific runtime, and separate memory subsystem. I would start with one or two product surfaces, keep the graph narrow, and earn the right to unify more objects later.

## Bottom line
`macro` is worth studying because it is one of the more serious open-source attempts at turning "AI workspace" into actual systems architecture. The repo's most convincing idea is not the marketing bundle of features; it is the combination of a shared graph, a real MCP surface, and a dedicated sync plane.

The builder lesson is that integration only becomes defensible when it is reflected in schemas, services, and runtime boundaries, not just in UI tabs.
