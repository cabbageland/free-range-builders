# Codex

- Repo: `openai/codex`
- URL: https://github.com/openai/codex
- Date: 2026-08-22
- Repo snapshot studied: `main` @ `343074d4207d572809bd8cea15f4be1d09d98e0b`
- Why picked today: GitHub's daily trending page showed `openai/codex` at the top when checked, with 4,159 stars added today and 112,716 total stars. More importantly, the repo is not a thin prompt wrapper. The source tree shows a real agent runtime: a Node launcher, a large Rust workspace, a TUI, a shell-execution/sandbox layer, a protocol crate, and Python and TypeScript SDKs around the same core.

## Executive summary
`openai/codex` is best understood as a native agent runtime with multiple packaging layers on top, not as an npm script with some API calls glued in. The clearest tell is [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js): the published `@openai/codex` package does not implement the agent itself, it chooses the right platform package and launches a bundled native executable. The real center of gravity is the Rust workspace declared in [`codex-rs/Cargo.toml`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/Cargo.toml), which pulls together a broad set of crates for core orchestration, TUI, login, MCP, sandboxing, cloud tasks, plugins, memories, and execution policy.

The most interesting architectural move is the split between UI, orchestration, protocol, and execution. [`codex-rs/tui/src/main.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/main.rs) is a thin CLI/TUI entrypoint; [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs) owns top-level application state and event wiring; [`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs) composes agent, config, connectors, context, MCP, plugins, realtime conversation, and execution modules; and [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs) implements the dangerous part carefully, with timeouts, output caps, network proxy support, and sandbox-manager integration.

The weak side is sprawl. The codebase is clearly serious, but it is also large enough that contributor orientation cost is real. The in-repo docs for some major topics are thin pointers to external docs, especially [`docs/config.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/docs/config.md), [`docs/sandbox.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/docs/sandbox.md), and [`docs/execpolicy.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/docs/execpolicy.md). The builder lesson is still strong: if you want an agent CLI to feel real, own the runtime boundaries instead of hiding them behind "magic."

## What they built
They built a local coding agent product with several distinct surfaces:

- A packaging layer in [`codex-cli`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli) that publishes the `@openai/codex` npm package and dispatches to native binaries.
- A large Rust monorepo in [`codex-rs`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs) that houses the CLI, TUI, core orchestration, protocol types, login flow, policy engine, sandboxing, MCP support, and extension infrastructure.
- SDK layers in [`sdk/typescript`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/typescript) and [`sdk/python`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python) so other programs can start and resume threads against the same runtime.
- Operational and contributor docs in [`docs`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/docs), plus maintenance tooling in [`tools`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/tools) and [`scripts`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/scripts).

## Why it matters
Many agent CLIs are mostly "prompt template plus subprocess pipe." `Codex` is worth studying because it clearly treats agent behavior as systems engineering:

1. The runtime is native and platform-specific instead of being forced through Node alone.
2. The protocol surface is explicit in [`codex-rs/protocol/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/protocol/src/lib.rs), which keeps approvals, capabilities, items, permissions, and plan/user-input structures from being scattered ad hoc through the UI.
3. The execution layer in [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs) visibly cares about output caps, cancellation, sandbox choice, and network policy instead of pretending shell execution is easy.
4. The SDKs are not afterthoughts. [`sdk/typescript/src/codex.ts`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/typescript/src/codex.ts), [`sdk/python/src/openai_codex/api.py`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python/src/openai_codex/api.py), and [`sdk/python/src/openai_codex/client.py`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python/src/openai_codex/client.py) expose thread lifecycle and runtime transport as reusable product surfaces.

## Layered architecture dissection
### High-level system shape
The high-level shape is: publish a tiny cross-platform launcher, hand off to a native Rust runtime, run the interactive TUI and session logic there, push protocol-typed events and approvals through a core orchestration layer, and isolate shell execution behind explicit policy and sandboxing.

### Main layers
**1. Distribution layer**  
[`codex-cli/package.json`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/package.json) and [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js) show that the npm package is mainly a delivery shim. The JavaScript chooses a target triple, resolves a platform package such as Linux/macOS/Windows bundles, and spawns the native executable. That keeps installation friendly while leaving the hard runtime work in Rust.

**2. CLI and TUI shell layer**  
[`codex-rs/tui/src/main.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/main.rs) parses config overrides and hands control to `run_main`. [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs) is the large application shell: approvals, app-server session bootstrapping, bottom-pane rendering, file search, external editor integration, multi-agent activity, and model migration are all wired here.

**3. Core orchestration layer**  
[`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs) is the composition root. Even the module list tells the story: `agent`, `apps`, `connectors`, `context`, `exec`, `guardian`, `mcp`, `plugins`, `realtime_conversation`, and `responses_retry` all live here. This is the layer that turns "a model plus tools" into a coherent local agent product.

**4. Protocol and policy layer**  
[`codex-rs/protocol/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/protocol/src/lib.rs) exposes modules for approvals, capabilities, dynamic tools, permissions, plan tools, request-user-input payloads, and turn input. [`codex-rs/execpolicy/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/execpolicy/src/lib.rs) packages the execution-policy parser, rules, evaluation, and migration support as a separate concern instead of burying it in shell code.

**5. Execution and safety layer**  
[`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs) is the key file if you care whether the product is production-minded. It integrates sandbox managers, network policy, cancellation, pty output caps, conventional timeout exit codes, and guarded stdout/stderr draining. This is the part many agent demos hand-wave away.

**6. External automation layer**  
[`sdk/typescript/src/codex.ts`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/typescript/src/codex.ts) provides start/resume thread primitives in TypeScript. [`sdk/python/src/openai_codex/api.py`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python/src/openai_codex/api.py) and [`sdk/python/src/openai_codex/client.py`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python/src/openai_codex/client.py) show the same strategy in Python, including runtime startup, login, turn execution, notification handling, and generated protocol bindings.

### Request / data / control flow
1. The user invokes `codex`, which starts in the npm-facing launcher at [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js).
2. That launcher picks the platform bundle and spawns the native binary exposed by the Rust workspace.
3. [`codex-rs/tui/src/main.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/main.rs) parses CLI/config state and enters `codex_tui::run_main`.
4. [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs) drives session state, approvals, rendering, and app-server interactions.
5. The core agent machinery under [`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs) coordinates threads, tools, MCP, connectors, plugins, and realtime conversation.
6. Any shell execution funnels through [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs), where sandbox and network decisions are enforced.
7. SDK clients wrap the same lifecycle: [`sdk/typescript/src/codex.ts`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/typescript/src/codex.ts) and [`sdk/python/src/openai_codex/api.py`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk/python/src/openai_codex/api.py) let external apps start or resume threads programmatically.

## Important components
The most important component is the native-launch boundary in [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js). It makes the packaging story pleasant without forcing the runtime to live in JavaScript.

The second is the TUI app shell in [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs). That file is where session management, approvals, bottom-pane UX, editor integration, and multi-agent UI come together.

The third is the orchestration root in [`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs). Its module surface makes clear that Codex is managing far more than chat turns.

The fourth is the execution path in [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs). If this file were sloppy, the rest of the product would be a safety liability.

The fifth is the shared protocol crate in [`codex-rs/protocol/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/protocol/src/lib.rs), because it keeps the agent's event and approval model explicit enough to reuse from SDKs.

## Practical questions and answers
**Is the npm package the agent runtime?**  
No. [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js) is a launcher that resolves a platform package and spawns a native executable.

**Where does the product's real complexity live?**  
Mostly in the Rust workspace under [`codex-rs`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs), especially [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs), [`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs), and [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs).

**Does the repo treat safety as a first-class systems problem?**  
Yes. [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs) visibly handles sandbox managers, network policy, cancellation, and output limits, while [`codex-rs/execpolicy/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/execpolicy/src/lib.rs) keeps policy parsing separate and inspectable.

**Is this only an interactive terminal UI?**  
No. The TypeScript and Python SDKs under [`sdk`](https://github.com/openai/codex/tree/343074d4207d572809bd8cea15f4be1d09d98e0b/sdk) make it clear the runtime is also meant to be embedded and automated.

**What would I read first if I wanted to understand it quickly?**  
Start with [`README.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/README.md), then [`codex-cli/bin/codex.js`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/bin/codex.js), [`codex-rs/Cargo.toml`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/Cargo.toml), [`codex-rs/tui/src/app.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/tui/src/app.rs), [`codex-rs/core/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/lib.rs), and [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs).

## What is smart
- Shipping a tiny JavaScript launcher over a native runtime instead of forcing the whole agent into one toolchain.
- Keeping protocol types centralized in [`codex-rs/protocol/src/lib.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/protocol/src/lib.rs), which makes SDK reuse and UI reuse saner.
- Treating shell execution as an engineered subsystem with caps, timeouts, cancellation, and sandbox integration in [`codex-rs/core/src/exec.rs`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/core/src/exec.rs).
- Building both Python and TypeScript SDKs around the same runtime rather than leaving users to scrape CLI output.

## What is flawed or weak
- [`codex-rs/Cargo.toml`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/Cargo.toml) reveals a huge workspace. That is power, but also real maintenance and onboarding overhead.
- [`codex-rs/README.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-rs/README.md), [`docs/config.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/docs/config.md), and [`docs/sandbox.md`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/docs/sandbox.md) often redirect to external docs instead of fully documenting the implementation in-repo.
- The packaging story spans npm, native bundles, platform-specific packages, and a large Rust workspace, which is flexible but adds mental overhead for contributors.
- [`codex-cli/package.json`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/codex-cli/package.json) declares `node >=16`, while the repo root [`package.json`](https://github.com/openai/codex/blob/343074d4207d572809bd8cea15f4be1d09d98e0b/package.json) expects newer repo-wide tooling. That split is practical, but it is another thing builders must keep straight.

## What we can learn / steal
- Put a friendly installer or wrapper in front of a stronger native runtime when the runtime deserves it.
- Separate UI, protocol, execution policy, and sandboxed shell plumbing instead of blending them into one giant loop.
- Expose a typed automation surface early so SDKs and embedded callers can use the same runtime.
- Treat agent execution controls as product architecture, not as "later hardening."

## How we could apply it
If we were building our own agent CLI, I would copy the boundary discipline more than the exact stack. A thin launcher, a central protocol crate or schema layer, a dedicated execution-policy engine, and a reusable SDK surface are the portable ideas here. I would try to avoid inheriting the whole workspace breadth on day one, but I would absolutely steal the notion that shell execution and approvals deserve first-class engineering.

## Bottom line
`openai/codex` is worth studying because it looks like a real agent operating environment, not a weekend wrapper around a model API.

The strongest builder lesson is that trustworthy local agents are mostly boundary design: packaging boundary, protocol boundary, UI boundary, and execution/sandbox boundary. Codex owns those boundaries in code, and that is why the repo feels substantial.
