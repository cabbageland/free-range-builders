## Executive summary
`llmfit` is a local-model planning engine disguised as a friendly TUI. The core crate under [`llmfit-core`](https://github.com/AlexsJones/llmfit/tree/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core) does the serious work: [`hardware.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/hardware.rs) probes RAM, CPU, and a surprisingly wide GPU matrix; [`fit.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/fit.rs) chooses quantization, estimates throughput, and computes composite ranking scores; [`models.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/models.rs) encodes the model-family heuristics and quant tables; and [`providers.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) turns those recommendations into runnable pulls against Ollama, llama.cpp, MLX, LM Studio, Docker Model Runner, and vLLM.

The product shape is unusually disciplined. [`llmfit-tui/src/main.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-tui/src/main.rs) exposes one binary that can behave as an interactive TUI, a JSON-speaking CLI for agents, a benchmark client, and a planning tool. The docs in [`docs/how-it-works.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/how-it-works.md), [`docs/providers.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/providers.md), and [`docs/openclaw.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/openclaw.md) make the architecture legible instead of hiding it behind magic.

The smartest move is that the repo treats "what should I run on this machine?" as a first-class systems problem with inspectable assumptions. The biggest weakness is that the answer still depends on embedded heuristics and curated catalogs. `llmfit` is honest about its estimates, but it is still an estimating machine before it is a benchmarking machine.

## What they built
They built a cross-platform local-LLM advisor with four connected surfaces:

- A hardware-detection and ranking core in [`llmfit-core`](https://github.com/AlexsJones/llmfit/tree/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core).
- A user-facing TUI and CLI entrypoint in [`llmfit-tui/src/main.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-tui/src/main.rs).
- An embedded data and benchmark catalog under [`llmfit-core/data`](https://github.com/AlexsJones/llmfit/tree/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data), including [`hf_models.json`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/hf_models.json), [`use_case_benchmarks.json`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/use_case_benchmarks.json), and [`benchmarks.yaml`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/benchmarks.yaml).
- Provider and automation integrations documented in [`docs/providers.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/providers.md) and the OpenClaw skill at [`skills/llmfit-advisor/SKILL.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/skills/llmfit-advisor/SKILL.md).

## Why it matters
Most local-model recommendation tools do one of two lazy things: they either benchmark one runtime on one machine, or they show a big table of model names with no serious hardware reasoning behind it. `llmfit` matters because it tries to bridge planning, installation, and verification:

1. It detects the machine rather than asking the user to hand-enter specs.
2. It scores models across quality, speed, fit, and context instead of pretending one number is enough.
3. It knows about runtime providers, not just model families.
4. It has a path from estimate to real measurement through `llmfit bench` and the community benchmark store.

## Layered architecture dissection
### High-level system shape
The high-level loop is simple and well chosen: detect the machine, load an embedded model catalog, simulate which quantizations and runtimes fit, score the candidates, then expose the answer through human and machine interfaces. If the user wants to act, provider adapters turn the chosen model into an install or pull request.

### Main layers
**1. Hardware detection layer**  
[`llmfit-core/src/hardware.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/hardware.rs) is the foundation. `SystemSpecs::detect()` reads RAM and CPU info through `sysinfo`, then fans out through `nvidia-smi`, ROCm, sysfs, WMI, Intel paths, Apple unified-memory handling, and even cluster-related fields. This is not "guess the GPU from `/proc`" toy code.

**2. Catalog and quantization layer**  
[`llmfit-core/src/models.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/models.rs) defines the quantization hierarchy, bytes-per-parameter estimates, quant speed multipliers, and model-family parsing logic. The embedded catalog files in [`llmfit-core/data`](https://github.com/AlexsJones/llmfit/tree/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data) give those heuristics something concrete to operate on.

**3. Fit and scoring layer**  
[`llmfit-core/src/fit.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/fit.rs) is the heart of the product. `CalcConfig` exposes the tunable estimation parameters. `RunMode` distinguishes GPU, MoE offload, CPU offload, CPU-only, and tensor-parallel paths. `ScoringWeights` varies the score composition by use case instead of flattening coding, chat, and embeddings into one universal ranking.

**4. Provider integration layer**  
[`llmfit-core/src/providers.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) abstracts runtime backends behind `ModelProvider`. The implementation is practical rather than academic: reachability probes, installed-model detection, name normalization, and async-ish pull progress events. [`docs/providers.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/providers.md) fills in the behavioral contract for Ollama, llama.cpp, MLX, Docker Model Runner, LM Studio, and remote hosts.

**5. Product and automation layer**  
[`llmfit-tui/src/main.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-tui/src/main.rs) turns the engine into a product: TUI by default, CLI subcommands, JSON output for agents, dashboard hosting, benchmark commands, and planning. [`docs/openclaw.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/openclaw.md) and [`skills/llmfit-advisor/SKILL.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/skills/llmfit-advisor/SKILL.md) show that the same core is intended to power agentic recommendation flows too.

### Request / data / control flow
1. [`SystemSpecs::detect()`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/hardware.rs) builds a normalized hardware snapshot.
2. The model database in [`hf_models.json`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/hf_models.json) and benchmark tables in [`use_case_benchmarks.json`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/use_case_benchmarks.json) load into the scoring path.
3. [`fit.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/fit.rs) selects the best quantization that fits, estimates throughput from bandwidth or backend constants, and scores candidates by use case.
4. [`llmfit-tui/src/main.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-tui/src/main.rs) renders those results to the TUI or returns structured JSON for scripts and agents.
5. If the user wants action, [`providers.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) translates a recommendation into an installed-model check or a provider-specific pull workflow.

## Important components
The most important component is [`CalcConfig`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/fit.rs). It makes the estimator adjustable instead of pretending the constants are universal truth.

The second is [`SystemSpecs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/hardware.rs), because every downstream recommendation is only as good as the hardware snapshot.

The third is the [`ModelProvider`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) trait, which lets the planner talk to actual local runtimes instead of staying a spreadsheet.

The fourth is the catalog/benchmark bundle in [`llmfit-core/data`](https://github.com/AlexsJones/llmfit/tree/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data), because that data is where most of the opinionated ranking value lives.

## Practical questions and answers
**Does it actually benchmark models, or mostly estimate them?**  
Mostly estimate first. [`docs/how-it-works.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/how-it-works.md) is explicit that the primary path is a bandwidth-driven estimator, with `llmfit bench` and community submissions used to ground or replace guesses.

**What is the strongest architectural idea here?**  
The separation between machine probing, scoring, and provider execution. [`hardware.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/hardware.rs), [`fit.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/fit.rs), and [`providers.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) each own one job.

**How fresh is the model knowledge?**  
Fresh enough to be useful, but not magically live. The catalog is embedded from [`hf_models.json`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/data/hf_models.json), and [`docs/how-it-works.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/how-it-works.md) makes clear that contributors refresh it and ship updates in releases.

**Where would it fail in production?**  
At the edges where provider behavior, quant naming, or new GPU families move faster than the heuristic tables. This repo is honest about that risk, but it cannot eliminate it.

## What is smart
- Treating model selection as a transparent planning problem instead of a vibes-based recommendation list.
- Publishing the estimation formulas and assumptions in [`docs/how-it-works.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/how-it-works.md) instead of hiding them.
- Separating core logic from TUI and desktop packaging through the workspace structure in [`Cargo.toml`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/Cargo.toml).
- Making provider integration concrete through [`providers.rs`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/llmfit-core/src/providers.rs) and [`docs/providers.md`](https://github.com/AlexsJones/llmfit/blob/acc7e40c3a0afbd36510a92f2f8f3d5177cfc0fe/docs/providers.md).

## What is flawed or weak
- The recommendation quality is only as durable as the embedded benchmark and naming tables, which means maintenance pressure never really stops.
- The speed estimator is admirably explicit, but still heuristic-heavy. If the constants drift, the confidence of the UX can outrun the truth of the machine.
- The repo tries to span many runtimes and many hardware backends at once, which is useful but invites a long tail of provider-specific bugs.
- The community benchmark path is a strong idea, but it still depends on the catalog and naming glue being correct enough to line results up with the right models and hardware.

## What we can learn / steal
- Separate detection, ranking, and execution into independent layers so each can evolve without rewiring the whole product.
- Show users the estimate basis instead of giving them a mysterious magic number.
- Use a compile-time catalog plus a documented refresh pipeline when live probing is too expensive or unreliable.
- Treat agent integration as another frontend over the same core, not a separate product.

## How we could apply it
If we ever need to recommend infra, local runtimes, or toolchains against messy host hardware, `llmfit` is a good pattern to copy. I would steal the explicit planner mindset, the tunable scoring configuration, and the provider abstraction. I would be even more aggressive about surfacing estimator confidence and data freshness, but the core architectural split is already strong.

## Bottom line
`llmfit` is worth studying because it turns a fuzzy consumer problem into a concrete systems product. The repo is not merely "a TUI for Ollama"; it is a layered advisor that joins hardware detection, model heuristics, provider adapters, and automation-friendly output into one coherent tool.

The builder lesson is that recommendation engines get more credible when they expose their assumptions. The caution is that once your product becomes the source of truth for fit and speed, your heuristics become part of the product surface and need the same maintenance discipline as code.
