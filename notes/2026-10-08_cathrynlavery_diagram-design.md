## Executive summary

[cathrynlavery/diagram-design](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9) is not a conventional app. It is a packaged design system and workflow layer for AI coding agents that need to make diagrams. The output target is deliberately simple: self-contained HTML files with inline SVG. The interesting engineering is around everything that makes that output reliable: skill instructions, type references, static templates, import/export commands, geometry rules, package manifests, screenshots, ADRs, and validators.

The repo's strongest idea is that diagram generation needs a grammar, not just a prompt. The core skill in [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) routes requests through visual types, semantic patterns, style tokens, connector rules, layout budgets, and taste gates. The large reference library under [skills/diagram-design/references](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references) turns those rules into per-diagram contracts. The examples under [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets) are not decorative samples; they are canonical fixtures for the grammar.

The repo is worth studying because it shows a repeatable pattern for turning taste into machine-checkable constraints. [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py) checks connector geometry and label masks. [scripts/verify-plugin-package.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-plugin-package.py) keeps native plugin packaging synchronized. [docs/adr](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr) explains why the taxonomy and release flow look the way they do.

## What they built

Diagram Design packages an Agent Skill that helps compatible coding agents produce editorial diagrams. The root [README.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/README.md) presents it as a way to make architecture diagrams, flowcharts, sequence diagrams, state machines, ER diagrams, charts, axonometric plans, and other visual forms as static HTML/SVG instead of generic boxes.

The repo ships that capability through several host surfaces. [`.codex-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.codex-plugin/plugin.json), [`.claude-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.claude-plugin/plugin.json), and [`.factory-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.factory-plugin/plugin.json) point host marketplaces at the same underlying skill directory. The command wrappers in [commands](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/commands) and prompt wrappers in [prompts](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/prompts) expose doctor, profile, import, and export flows without forking the core instructions.

Inside the skill, [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) is the router and taste contract. The specific visual grammars live in files such as [references/type-architecture.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-architecture.md), [references/type-tree.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-tree.md), and [references/type-sankey.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-sankey.md). ## Why it matters

Most AI-generated diagrams fail because the model has no stable contract for density, hierarchy, connectors, typography, output size, export behavior, or visual type selection. This repo treats that as an engineering problem. Instead of saying "make it pretty," [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) gives the agent explicit rules: choose a semantic pattern when behavior carries meaning, choose a type reference for layout, keep coral accents rare, avoid diagonal connectors, keep label masks clear, use fixed size presets, and verify.

It also matters because it is a good example of skill packaging as product. The plugin manifests are thin, but they make the same skill usable across Codex, Claude Code, Factory Droid, and other hosts. The core assets are portable static files. The validators are plain Python. The ADRs explain why the taxonomy is constrained. A builder can steal the general shape for any high-taste agent workflow: one skill file as router, focused references as contracts, canonical examples as fixtures, and validators for the failures that humans keep missing.

## Layered architecture dissection

### High-level system shape

The repo has four layers.

The first layer is product packaging. [`.codex-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.codex-plugin/plugin.json) declares the plugin name, version, description, category, capabilities, icon, marketplace copy, and `skills` pointer. The equivalent [`.claude-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.claude-plugin/plugin.json) and [`.factory-plugin/plugin.json`](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/.factory-plugin/plugin.json) keep host-specific installation thin.

The second layer is agent instruction. [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) is the main control plane. It decides when to use the skill, how to gate first-time style setup, how to route semantic patterns to visual types, what anti-patterns to avoid, what primitives are legal, what output sizes mean, and what checks should run before delivery.

The third layer is reusable diagram grammar. [skills/diagram-design/references](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references) contains the detail the main skill cannot hold without becoming unreadable. [references/type-architecture.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-architecture.md) defines architecture diagram layout conventions and connector routing. [references/output-spec.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/output-spec.md) defines size presets, export expectations, and detail levels. [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md) defines how an HTML diagram becomes SVG or PNG.

The fourth layer is enforcement and artifact generation. [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py), [scripts/lint-render.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/lint-render.py), [scripts/verify-docs-sync.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-docs-sync.py), [scripts/verify-block-registry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-block-registry.py), and [scripts/verify-plugin-package.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-plugin-package.py) turn taste and packaging rules into executable checks.

### Main layers

The skill-router layer is opinionated. [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) explicitly says the agent should avoid diagrams when a paragraph or table is better. That negative guidance is as important as the type catalog. It prevents the tool from becoming a "diagram everything" generator.

The visual-type layer is modular. Each type reference owns a layout grammar. For example, [references/type-architecture.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-architecture.md) describes zones, orthogonal connector routing, port selection, dashed path semantics, bridge hops, and anti-patterns. That lets the main skill stay short enough to route while leaving type-specific rules close to examples.

The primitive layer is shared. [references/primitives-core.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/primitives-core.md) defines node boxes, arrows, labels, masks, and connector rules that apply across types. [references/primitive-icons.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/primitive-icons.md), [references/primitive-annotation.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/primitive-annotation.md), [references/primitive-sketchy.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/primitive-sketchy.md), and [references/primitive-terminal.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/primitive-terminal.md) add optional visual vocabulary without changing the base output contract.

The artifact layer is static by default. [skills/diagram-design/assets/template.html](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets/template.html), [skills/diagram-design/assets/template-dark.html](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets/template-dark.html), [skills/diagram-design/assets/template-full.html](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets/template-full.html), and [skills/diagram-design/assets/template-motion.html](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets/template-motion.html) are starting points. The examples under [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets) demonstrate the grammar in full.

The governance layer is unusually explicit. [docs/adr/0001-static-by-default-single-pinned-controller.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0001-static-by-default-single-pinned-controller.md) explains the static-by-default stance. [docs/adr/0002-semantic-patterns-do-not-expand-the-taxonomy.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0002-semantic-patterns-do-not-expand-the-taxonomy.md) explains why semantic patterns should not explode the type count. [docs/adr/0010-block-registry-metadata-contract.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0010-block-registry-metadata-contract.md) shows how a new traceable-block pattern was routed to Tree instead of adding a new type.

### Request / data / control flow

A normal diagram request enters through the host's skill system and lands in [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md). The first decision is whether a diagram is warranted. If yes, the skill checks the style-guide gate and profile rules through [references/profiles.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/profiles.md), [references/onboarding.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/onboarding.md), and [references/style-guide.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/style-guide.md).

Next, the skill routes the content. If behavior or risk carries the meaning, it reads [references/semantic-patterns.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/semantic-patterns.md) and maps the request to a nearest visual type. Otherwise it picks a type directly and loads the matching file, such as [references/type-architecture.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-architecture.md). It then uses [references/output-spec.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/output-spec.md) and [references/layout-budget.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/layout-budget.md) to decide canvas size, detail level, and complexity budget.

The generated artifact is a standalone HTML file based on the templates under [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets). Export is intentionally a separate command path. [commands/export-diagram.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/commands/export-diagram.md) delegates to [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md), which prefers [skills/diagram-design/scripts/export_svg.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/scripts/export_svg.py) when available and describes how PNG capture should work through Playwright.

## Important components

The main component is the skill body in [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md). It is long because it owns taste, routing, and safety. The most useful parts are not the diagram list; they are the rules that suppress low-value diagrams, force style-guide setup, and require loaded type references before drawing.

The reference library under [skills/diagram-design/references](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references) is the second component. It externalizes the details that would otherwise bloat the skill file. The pattern is reusable: make the top-level skill a router, then put detailed contracts in small files that the agent loads only when needed.

The assets under [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets) are both examples and regression material. A repo with dozens of visual grammars needs canonical examples, not just prose. The examples also make screenshot generation and visual docs possible.

The validator scripts under [scripts](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts) are the enforcement layer. [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py) is especially interesting because it converts subjective "that connector looks wrong" feedback into concrete geometric checks.

The ADRs under [docs/adr](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr) are product memory. [docs/adr/0010-block-registry-metadata-contract.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0010-block-registry-metadata-contract.md) is the standout because it shows restraint: traceable block decomposition becomes a semantic pattern on Tree, not a new diagram type, and rich metadata goes in `data-block-*` attributes plus a generated registry instead of crowding the canvas.

## Important knobs / configs / extension points

The first extension point is the style system in [references/style-guide.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/style-guide.md). The skill is designed to be skinned by semantic roles rather than one-off color picks. The repo's first-time setup gate in [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) makes that operational: in a branded project, the agent should not silently ship default-looking diagrams.

The second is visual-type selection. Adding a type is intentionally expensive because it must include a reference, examples, screenshots, budget rows, and sync checks. The easier extension route is semantic patterns in [references/semantic-patterns.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/semantic-patterns.md), which can route behavior-specific meaning onto existing layout grammars.

The third is export behavior. [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md) has detailed rules for SVG extraction, CSS carry-forward, XML safety, namespaced defs IDs, rgba normalization, and PNG capture. That is a lot of machinery, but it is exactly where diagram tools often fail.

The fourth is packaging. [scripts/verify-plugin-package.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-plugin-package.py) treats synchronized manifest versions, marketplace identity, and local paths as a checked contract. [docs/adr/0009-versions-are-bumped-on-main-after-merge.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0009-versions-are-bumped-on-main-after-merge.md) explains why version bumping belongs in the main-branch release flow.

## Practical questions and answers

Q: Is this mostly prompt engineering?  
A: No. The prompts matter, but the system is a packaged design grammar. [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) routes and constrains the agent, [skills/diagram-design/references](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references) defines grammar, [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets) supplies examples, and [scripts](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts) checks failures.

Q: Why static HTML/SVG instead of a diagram app?  
A: Static output is the product constraint. [docs/adr/0001-static-by-default-single-pinned-controller.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0001-static-by-default-single-pinned-controller.md) records that static is the default, while [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md) explains how static HTML becomes portable SVG or PNG. That makes diagrams easy to inspect, version, embed, and export.

Q: Where is the real quality control?  
A: Partly in prose, partly in tests. [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) states the design rules, but [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py), [scripts/lint-render.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/lint-render.py), and many `scripts/test-*` files turn key failures into repeatable checks.

Q: What is the easiest thing to copy?  
A: Copy the router/reference split. Put high-level behavior in one skill file, but move detailed grammar into focused references such as [references/type-architecture.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/type-architecture.md) and [references/output-spec.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/output-spec.md). That keeps the main prompt from becoming a dump.

Q: What is the highest-risk part?  
A: The repo's value depends on agent compliance. The more hosts it supports, the more it needs the packaging checks in [scripts/verify-plugin-package.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-plugin-package.py) and the rendering checks in [scripts/lint-render.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/lint-render.py). A host that ignores skill-loading or file-reading conventions can still produce weak diagrams.

## What is smart

The smartest move is constraining taste into named contracts. "No diagonal connectors" is not merely a style preference; [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py) can check it. "Do not cram every fact into one visual" becomes a budget in [references/layout-budget.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/layout-budget.md) and [references/output-spec.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/output-spec.md). "Use the nearest existing type" becomes an ADR-backed taxonomy rule in [docs/adr/0002-semantic-patterns-do-not-expand-the-taxonomy.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0002-semantic-patterns-do-not-expand-the-taxonomy.md).

The export path is also smart. [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md) recognizes that extracting an SVG from styled HTML is not trivial. It preserves accessibility names, carries scoped CSS, namespaces marker IDs, imports fonts safely, and normalizes colors for consumers that mishandle `rgba()`.

The repo uses ADRs well. [docs/adr/0010-block-registry-metadata-contract.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0010-block-registry-metadata-contract.md) is not bureaucratic filler; it captures a real product decision about metadata, visible density, sidecar generation, and why IDEF0 was rejected.

## What is flawed or weak

The scope is broad. Forty-plus visual types means a lot of references, assets, screenshots, and checks. The modular reference layout helps, but every new type increases cognitive load for contributors and for agents reading the skill.

The system relies on host behavior. The plugin files can expose [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md), but each agent host still needs to load references, follow file-reading rules, write HTML correctly, and run checks. The repo can guide and verify some outputs, but it cannot fully control the agent runtime.

The static-HTML approach is elegant but can make rich editing awkward. [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md) is careful because export is genuinely tricky. Once a diagram leaves the browser, fonts, CSS scoping, markers, clipping, and presentation tools can all become failure points.

The README markets a huge capability surface. [README.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/README.md) is compelling, but the real value is in the narrower operational discipline: a good agent reads the right reference and produces one useful diagram. A careless agent can still create a polished-looking bad visual.

## What we can learn / steal

Steal the separation between routing and grammar. A durable agent skill should not put every rule in one giant instruction file. [skills/diagram-design/SKILL.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/SKILL.md) routes; [skills/diagram-design/references](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references) specializes.

Steal executable taste gates. [scripts/verify-geometry.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-geometry.py) is the pattern: find the repeated human complaint, define a conservative detector, and make it part of the workflow.

Steal static canonical examples. [skills/diagram-design/assets](https://github.com/cathrynlavery/diagram-design/tree/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/assets) gives agents and humans a shared visual target. That is much stronger than prose alone.

Steal the ADR discipline for taste decisions. [docs/adr/0010-block-registry-metadata-contract.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/docs/adr/0010-block-registry-metadata-contract.md) shows how to keep a design system from accreting new categories for every request.

## How we could apply it

For any agent workflow that produces durable artifacts, I would copy this shape: a thin host manifest, a main skill router, small references for specific output types, a style or policy file, canonical examples, and validators for known failure modes.

For developer documentation, I would copy the static artifact choice. HTML with inline SVG is reviewable, diffable, renderable in a browser, and exportable. The hard part is the discipline around it, which this repo encodes in [references/output-spec.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/output-spec.md) and [references/export.md](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/skills/diagram-design/references/export.md).

For skill or plugin packaging, I would copy [scripts/verify-plugin-package.py](https://github.com/cathrynlavery/diagram-design/blob/f4547ee95f88e5b28a52517feff6b6c11cc657f9/scripts/verify-plugin-package.py)'s habit of checking synchronized host manifests instead of assuming every marketplace file stayed aligned.

## Bottom line

Diagram Design is a strong example of agent-product engineering because it treats visual quality as a system of contracts: routing, references, templates, examples, validators, ADRs, and host packaging. The reusable lesson is not "AI can draw diagrams." It is that taste becomes scalable only when the workflow names its rules, ships examples, and checks the failure modes that matter.
